## R-1 สร้างรูป QR บนหน้าผู้สูงอายุ (NEEDS CLARIFICATION → **ตัดสินแล้ว 22/10/69 โดย A**)

FR-01 ✓1 ต้อง "เห็น QR" แต่ `prototype/vendor/` มีแค่ตัว**อ่าน** QR (jsQR) ไม่มีตัว**สร้าง** และไม่มีเอกสารใดในทีมตัดสินเรื่องนี้

- **Decision:** เพิ่ม `qrcode-generator@1.4.4` (Kazuhiko Arase · MIT · ไฟล์เดียว `qrcode.js` · ไม่มี dependency · ออก 18 ก.ย. 2019)
  ไว้ที่ `prototype/vendor/qrcode/` · `qrScan.qrMatrix(code)` คืนตาราง boolean (`isDark`) → หน้าจอวาดลง canvas · ระดับแก้ผิด M
  (ไม่ใช้ `createSvgTag()` เพราะคืนข้อความ HTML ต้องใช้ innerHTML ซึ่ง shell ห้าม)
- **Rationale:** FR-01 ✓1 บังคับ → ไม่ใช่ gold-plating · ไฟล์เดียว UMD ใช้ได้ทั้ง `file://` และ `node --test` · ใช้มานานหลายปี ·
  ตรวจที่ npm registry แล้ว (22/10/69): 1.4.4 มีจริง license MIT · เลือก 1.x ไม่ใช่ 2.0.4 (ส.ค. 2025) เพราะ 1.x มีไฟล์ UMD
  ไฟล์เดียวที่เสถียรและไม่มี ESM ให้สับสน
- **ตรวจแล้ว (22/10/69):** tarball จาก npm → sha512 ตรงกับ `integrity` ใน registry · `dependencies` ว่าง · ไม่มี fetch/XHR/eval/DOM ในไฟล์ ·
  สร้าง `MEDMIND:004213` (21×21 โมดูล) แล้ว jsQR ใน vendor อ่านกลับได้ถูก (38 ms) · บันทึกใน `vendor/README.md`, TEAM-PLAN ข้อ 4, ADR-07
- **Alternatives:**
  - เขียนตัวเข้ารหัส QR เอง → ปฏิเสธ: Reed–Solomon + mask หลายร้อยบรรทัด ผิดง่าย ไม่ใช่แก่นของ FR
  - โหลดจาก CDN → ปฏิเสธ: ใช้ไม่ได้เมื่อไม่มีเน็ต · ขัดหลัก "เก็บในเครื่อง ไม่โหลดจาก CDN" ของ vendor
  - แสดงแค่รหัส 6 หลัก ไม่มี QR → ปฏิเสธ: ไม่ผ่าน ✓1 และ ✓3 (สแกน QR)
  - รูป QR ทำไว้ล่วงหน้า → ปฏิเสธ: รหัสสุ่ม 1,000,000 แบบ ทำล่วงหน้าไม่ได้

## R-2 อ่าน QR: กล้องสด + ทางสำรองรูป (ADR-07 · ✓3, ✗7) — **แก้ 22/10 หลังทดสอบบนมือถือ**

- **Decision (ปัจจุบัน):** ปุ่มหลัก "สแกน QR" เปิดกล้องหลังสด (`getUserMedia({ video: { facingMode: "environment" }, audio: false })`) → อ่านเฟรมละ 200 ms ย่อด้านยาว ≤ 640 px → `readQr` · เจอรหัสของเรา → ปิดกล้อง (ปิดไฟกล้อง) แล้ว `pair` ทันที · เฟรมที่ไม่มี QR → เล็งต่อ ไม่นับครั้งผิด
  ไม่อนุญาต/เปิดไม่ได้ → ข้อความ ✗7 + โฟกัสช่องรหัส · ไม่มี `mediaDevices` → เปิดตัวเลือกรูปแทน · ปุ่มรอง "เลือกรูป QR จากเครื่อง" มีเสมอ
  ล็อก (BR-18)/จับคู่แล้ว/ออกจากหน้า → ปิดกล้องเอง · `draw()` ซ้ำ (เวลาจำลองเดิน) ใช้ `<video>` ตัวเดิม ไม่เปิดกล้องใหม่
- **เหตุที่กลับคำตัดสิน:** ร่างแรกเลือกถ่ายรูปอย่างเดียวเพราะคิดว่ากล้องสดซับซ้อน แต่ผู้ใช้ทดสอบบนมือถือแล้วไม่เห็นภาพกล้อง และ AC ✗7 พูดถึง "ไม่อนุญาตกล้อง" → ตีความของ AI คลาดจากความคาดหวังของผู้ใช้ · ไม่เพิ่ม dependency (ใช้ jsQR เดิม)
- **ข้อจำกัด:** กล้องสดต้อง HTTPS บนมือถือ (ลิงก์ GitHub Pages) · เปิดแบบ `file://` บนเดสก์ท็อปใช้ได้ใน Chrome แต่ถามสิทธิ์ทุกครั้ง

### R-2 (ร่างเดิม — ทางสำรองรูป ยังใช้อยู่)

- **Decision:** `<input type="file" accept="image/*" capture="environment">` → วาดรูปลง canvas (ย่อด้านยาวสุด ≤ 1024 px) →
  `getImageData` → `jsQR(data, w, h)` → `codeFromQr(result.data)` · ไม่ได้ → ข้อความ ✗7 และโฟกัสช่องใส่รหัส
- **Rationale:** ทำงานได้ทั้ง `file://` และ HTTPS (TEAM-PLAN 5.1 ทดสอบแล้ว) · รูปจากผู้ใช้ไม่ทำให้ canvas tainted · ย่อรูปทำให้รูปมือถือ
  12 MP อ่านเร็วขึ้นและไม่กินหน่วยความจำ
- **"ไม่อนุญาตกล้อง":** เลือกรูปผ่าน file input ไม่ต้องขอสิทธิ์กล้องจากหน้าเว็บ · ถ้าผู้ใช้ปิดตัวเลือกรูป/ไม่ได้รูป → ช่องใส่รหัสแสดงอยู่แล้วเสมอ
  (ทางสำรองไม่ต้องรอ error)
- **Alternatives:** สแกนสดจากวิดีโอ (`getUserMedia`) → ปฏิเสธใน ADR-07 (ต้อง HTTPS, ซับซ้อนกว่า, ไม่จำเป็นต่อ AC)

## R-3 กฎล็อก BR-18 — นิยามที่ไม่ปลดล็อกก่อนเวลา (แก้สัญญา `architecture.md` §8.3)

สัญญาเดิมเขียนว่า "ล็อกเมื่อมีครั้งผิด ≥ 5 ในช่วง `(now − 10 นาที, now]`" → **ผิด**: ผิด 4 ครั้งที่ t และครั้งที่ 5 ที่ t+9 นาที
ควรล็อกถึง t+19 แต่ที่ t+10.5 นาที ช่วงนั้นเหลือครั้งผิด 1 ครั้ง → ปลดล็อกเร็วไป 8.5 นาที

- **Decision:** ให้ L = ครั้งผิดล่าสุดของผู้ดูแลคนนั้น · ล็อกเมื่อ (จำนวนครั้งผิดในช่วง `(L − 10 นาที, L]` ≥ 5) **และ** `now < L + 10 นาที` →
  `retryAt = L + 10 นาที` · ระหว่างล็อกไม่เพิ่มครั้งผิด จึง L = ครั้งที่ 5 เสมอ (ตรง R9 "ครั้งผิดที่ 5 + 10 นาที")
- ค่าขอบ: `now = L + 10 นาที` พอดี → ปลดล็อก · ครั้งที่ 5 ตรวจรหัสตามปกติ (ได้เหตุผลของรหัสนั้น) แล้วผลลัพธ์มี `retryAt`
- เก็บน้อยที่สุด (NFR-09): `pair` ลบครั้งผิดที่ `failedAt ≤ now − 20 นาที` · **แก้ตอน implement 22/10:** ร่างแรกเขียน "≤ now − 10 นาที"
  แต่ test ค่าขอบ (T018) จับได้ว่าทำให้ปลดล็อกก่อนเวลา — ล็อกที่ยังมีผลตอน now ต้องมี L > now − 10 และครั้งผิดของมันอยู่ใน (L − 10, L]
  จึงต้องเก็บย้อนหลัง 10 + 10 = 20 นาที · เก่ากว่านั้นไม่มีผลต่อการตัดสินใด ๆ อีก
- **Alternatives:** นับในช่วง `(now − 10, now]` (ปฏิเสธ: ปลดเร็ว) · เก็บ `lockedUntil` เป็นฟิลด์ (ปฏิเสธ: ค่าคำนวณได้ ไม่เป็นฟิลด์ — กติกาวิชา)

## R-4 รหัสเชิญ: สุ่ม · ซ้ำ · รหัสเดิม

- **Decision:** `code = String(floor(random() × 1,000,000))` เติม 0 หน้าให้ครบ 6 หลัก ("000123" ใช้ได้) · ถ้าซ้ำกับรหัสใดใน `invites`
  สุ่มใหม่ (สูงสุด 20 ครั้ง แล้ว throw) → `pair` ค้นด้วย `code` ได้ไม่เกิน 1 รายการเสมอ · `newInvite` ลบรหัสที่ยังไม่ใช้ของผู้สูงอายุคนนั้น (clarify Q4)
- `random` ส่งเข้ามา (ค่าเริ่ม `Math.random` ที่หน้าจอ) → test ส่งลำดับค่าคงที่ได้ · Math.random พอสำหรับ prototype
  (ป้องกันการเดาด้วย BR-18 ไม่ใช่ด้วยความสุ่ม) · ระบบจริง (M4) ต้องสุ่มที่ server
- **Alternatives:** `crypto.getRandomValues` → ไม่จำเป็นใน prototype และ test ยากกว่า (บันทึกเป็นงาน M4)

## R-5 รหัสเครื่อง (ADR-05)

- **Decision:** เพิ่ม operation `ensureDevices(devices, now, random)` → `{ seniorId, caregiverId, createdAt }` เติมเฉพาะที่ยังไม่มี ·
  รหัส = `"S-"`/`"C-"` + ตัวอักษรสุ่ม 8 ตัว · เก็บใน `devices` (1 เบราว์เซอร์จำลอง 2 เครื่อง SRS §2.2)
- **Rationale:** สัญญา §8.3 ไม่ได้บอกว่าใครสร้าง `devices` → ต้องมีที่อยู่ที่ test ได้ (ไม่ใช่ในหน้าจอ) · ไม่มีข้อมูลส่วนตัว
- **ต้องแก้:** เพิ่มแถว `ensureDevices` ใน `architecture.md` §8.3 (ทำในงานนี้)

## R-6 ข้อความเหตุผลปฏิเสธอยู่ที่ไหน (SC-005, ✗5 ✗7 ✗8 ระบุข้อความตรงตัว)

- **Decision:** `reasonText(reason, minutesLeft)` อยู่ในโมดูล `pairing` (test ได้) · เพิ่มเป็นข้อยกเว้นใน `architecture.md` §8.1 ร่วมกับ BR-13/14/15
- **Rationale:** AC ✗5 ✗7 ✗8 กำหนดข้อความตรงตัว → constitution III ให้ทุก AC มี test · หน้าจอทดสอบด้วย `node --test` ไม่ได้
- **Alternatives:** ข้อความในหน้าจอ (ปฏิเสธ: test อัตโนมัติไม่ได้ เหลือแค่ทดสอบมือ)

## R-7 สองแท็บกดพร้อมกัน (edge case ADR-06)

- **Decision:** ตัวจัดการปุ่มของหน้าจอ (ไม่ใช่ render) เรียก `store.reload()` ก่อนอ่านข้อมูลเพื่อเรียก `newInvite` / `consent` / `pair` / `unpair` แล้วเขียนกลับทันที
  · ห้ามเรียกใน render เพราะ `reload()` แจ้งผู้ฟังทุกครั้ง → render วนไม่จบ (`/speckit-analyze` C1 · tasks.md "กติกาหน้าจอ")
  (localStorage เขียนแบบ synchronous ในแท็บเดียว) · `pair` ตรวจ `pairing` ที่มีอยู่ → `ALREADY_PAIRED` / รหัส `usedAt` → `USED`
- **Rationale:** ช่องว่างเหลือแค่ระดับมิลลิวินาทีระหว่างแท็บในเบราว์เซอร์เดียวกัน · ยอมรับใน prototype · ระบบจริงต้องตรวจที่ server (M4)
- **Alternatives:** ล็อกข้ามแท็บ (Web Locks / BroadcastChannel) → ปฏิเสธ: เพิ่มกลไกที่ไม่มี FR บังคับ

## R-8 การกลับหน้าจับคู่เมื่อถูกยกเลิก (R6 · ✗6)

- **Decision:** ทุกหน้าจอของผู้ดูแล (C1–C3) และผู้สูงอายุ (S1–S3) ที่อ่านข้อมูลคู่ ต้องเรียก `canAccess` ตอน render และใน `ctx.subscribe` ·
  ไม่ผ่าน → `ctx.go('C1', { notice: 'UNPAIRED' })` / `ctx.go('S1')` · C1 แสดง "การจับคู่ถูกยกเลิกแล้ว" เมื่อได้ `notice`
- **Rationale:** shell ไม่มี hook ทั้งแอป และ R7 กำหนดให้ feature อื่นเรียกตัวตรวจสิทธิ์อยู่แล้ว → ไม่ต้องเพิ่มกลไกใหม่ใน Foundation
- **ตัดสินแล้ว 22/10 (A):** บังคับใน `architecture.md` §8.5 · B (C2), C (S2), D (S3), E (C3) ทำตาม [contracts/screens.md](contracts/screens.md)

## R-9 เมื่อรหัสหมดอายุบนหน้าผู้สูงอายุ

- **Decision:** ไม่สร้างใหม่เอง · แสดง "รหัสหมดอายุแล้ว" + ปุ่มหลัก "สร้างรหัสใหม่" (1 ปุ่มหลัก/หน้าจอ) · หน้าแรกที่ยังไม่มีรหัสเลย → สร้างให้ทันที (✓1)
- **Rationale:** การยินยอมผูกกับรหัส (Assumption) → สร้างใหม่เองทุก 10 นาทีทำให้การยินยอมหายโดยผู้ใช้ไม่รู้
- **Alternatives:** สร้างใหม่อัตโนมัติ → ปฏิเสธ: ผู้สูงอายุที่ยินยอมแล้วต้องกดยินยอมใหม่โดยไม่รู้สาเหตุ
