# Research: เตือนเมื่อถึงมื้อยา (003-reminder)
<!-- เจ้าของ: C (Takkan Khanlui) · ร่างโดย A ตามที่ทีมตัดสิน 23/10/69 · Claude Code /speckit-plan -->

ไม่มีช่อง NEEDS CLARIFICATION เหลือใน spec · ข้อด้านล่างคือการตัดสินใจทางเทคนิคที่ spec ปล่อยให้ plan

## R-1 มื้อยามาจาก `reminderTimes` ของ FR-02 ไม่คำนวณซ้ำ

- **Decision:** `sessionsOf(medications, mealTimes, day)` เรียก `MedMind.medication.reminderTimes(med, mealTimes)` ต่อยา → จัดกลุ่มตามเวลา "HH:MM" → 1 กลุ่ม = 1 มื้อ · `sessionKey = day + '@' + HH:MM` · `at` = ms ของเวลานั้นในวัน `day` (เวลาท้องถิ่น)
- **Rationale:** BR-06 อยู่ที่เดียว (FR-02 test แล้ว ✓6 ✓8 ✓9) · ยาที่ `reminderTimes` = `null` ไม่อยู่ในมื้อใด (ไม่เดา)
- **Alternatives:** คำนวณเวลาจากฉลากซ้ำใน doseSession — กฎซ้ำ 2 ที่ แก้ที่หนึ่งแล้วอีกที่ผิด (cohesion)

## R-2 รอบเตือนเป็นค่าคำนวณจาก `at` + `now`

- **Decision:** `roundAt(session, now)` = `floor((now − at) / 5 นาที) + 1` เมื่อ `at ≤ now < at + 15 นาที` · ก่อน `at` = `0` · ตั้งแต่ `at + 15` = `null` (ตามสัญญา architecture §8.3)
- **Rationale:** เวลาคงที่จาก T (BR-08) · นาฬิกาจำลองกระโดดข้ามรอบได้ (demo bar +15) → ได้รอบปัจจุบันเสมอ ไม่ต้องเก็บสถานะ
- **Alternatives:** `setTimeout` ต่อรอบ — ADR-02 ปฏิเสธแล้ว (test ต้องรอจริง)

## R-3 มื้อข้ามเที่ยงคืน

- **Decision:** หน้าจอส่งมื้อของ **เมื่อวาน + วันนี้** ให้ `dueSessions` (`dayOf(now, -1)`, `dayOf(now, 0)`) · มื้อ 23:55 รอบ 2–3 (00:00, 00:05) ยังเป็นมื้อวันเดิม
- **Rationale:** NFR-01 "ทุกครั้ง" รวมมื้อดึก · มื้อของเมื่อวานที่ยังไม่ถึง T+15 มีได้ไม่เกิน 15 นาทีหลังเที่ยงคืน
- **Alternatives:** ส่งเฉพาะวันนี้ — มื้อ 23:50 ขึ้นไปเตือนไม่ครบ 3 รอบ (ขัด NFR-01)

## R-4 ช่วงยืนยันช้า (clarify 23/10) อยู่ใน `doseSession.lateUntil`

- **Decision:** `lateUntil(session, sessions)` = `at` ของมื้อถัดไปในวันเดียวกันที่ `at > session.at + 15 นาที` · ไม่มี = 00:00 ของวันถัดไป (= "ถึง 23:59" ของ BR-15) · ผลไม่น้อยกว่า `at + 15` (มื้อดึกที่ T+15 เลยเที่ยงคืน → ช่วงยืนยันช้าว่าง) · อยู่ในช่วงเมื่อ `at + 15 ≤ now < lateUntil`
- **Rationale:** สัญญา architecture §8.3 วาง `lateUntil` ไว้ใน `doseSession` แล้ว · R6b ของ spec ต้องใช้ · FR-04 (`confirm`) ใช้ตัวเดียวกัน → กฎ BR-15 อยู่ที่เดียว · ค่าขอบตรง FR-04 ✗6 (12:00 = มื้อถัดไป → ยืนยันไม่ได้)
- **Alternatives:** ให้ FR-04 ทำ `lateUntil` — S2 ต้องรอ FR-04 และเสี่ยงสองโมดูลนิยามต่างกัน

## R-5 `dueSessions` คืนมื้อพร้อมรอบ และมื้อช่วงยืนยันช้าเฉพาะเมื่อมีมื้อกำลังเตือน

- **Decision:** `dueSessions(sessions, confirmations, pairingId, now)` → `[{ sessionKey, at, medicationIds, round, late }]` เรียงตาม `at` ·
  มื้อที่ยืนยันแล้ว (มี `confirmations` ของ `pairingId` + `sessionKey` นั้น) ถูกตัดออก ·
  `round` 1–3 = กำลังเตือน (`late: false`) · ไม่มีมื้อกำลังเตือน → `[]` · มีอย่างน้อย 1 มื้อ → เพิ่มมื้อช่วงยืนยันช้า (`round: null`, `late: true`)
- **Rationale:** ✓3 ✗4 R6b ทดสอบได้ด้วยฟังก์ชันเดียว · หน้าจอไม่ต้องรู้กฎ · `pairingId` กันบันทึกยืนยันของคู่อื่น (NFR-04)
- **Alternatives:** คืนแค่มื้อรอบ 1–3 ตามสัญญาเดิม แล้วหน้าจอเติมมื้อช่วงยืนยันช้าเอง — กฎหลุดไปอยู่ในหน้าจอ (constitution III)
- **ผลต่อสัญญา:** แก้ `architecture.md` §8.3 ช่อง `dueSessions` (เพิ่ม `pairingId`, รูปผล, R6b) + เพิ่ม `dayOf`, `newSoundKeys` ในงานเดียวกัน

## R-6 เสียง: 1 ครั้งต่อรอบต่อเวลาเตือน (BR-09, BR-16)

- **Decision:** `newSoundKeys(due, played)` (ฟังก์ชันล้วน) → คีย์ `at + '#' + round` ของมื้อ `late: false` ที่ยังไม่อยู่ใน `played` (ไม่ซ้ำ) · หน้าจอเล่นเสียง 1 ครั้งเมื่อผลไม่ว่าง แล้วเพิ่มคีย์ลง `played` (ในหน่วยความจำของหน้า ไม่เก็บใน store)
- **Rationale:** มื้อเวลาเดียวกันรวมเป็นมื้อเดียวอยู่แล้ว (R-1) · หลายมื้อขึ้นรอบในการวาดครั้งเดียว = เล่น 1 ครั้ง · วาดซ้ำในรอบเดิม = ไม่มีคีย์ใหม่ · กระโดดข้ามรอบ = คีย์ของรอบปัจจุบันเท่านั้น (SC-004)
- **Alternatives:** เก็บ "เล่นแล้ว" ใน store — เขียนข้อมูลเพราะการเตือน (spec: การเตือนไม่เขียนข้อมูล) และทุกแท็บชนกัน

## R-7 สร้างเสียงด้วย Web Audio ในหน้า

- **Decision:** `AudioContext` + `OscillatorNode` เล่นเสียง 3 จังหวะสั้น (~1.2 วินาที) · สร้าง context ครั้งแรกเมื่อผู้ใช้แตะหน้า (`pointerdown`/`keydown` บน document) → `resume()` · ยังไม่แตะ = แสดงข้อความ "แตะหน้าจอ 1 ครั้งเพื่อเปิดเสียงเตือน" แทนการเล่น
- **Rationale:** ไม่มีไฟล์เสียง → ดับเบิลคลิก (`file://`) ได้ ไม่ต้องฝังไฟล์ (R12) · ไม่มี dependency ใหม่ · นโยบาย autoplay ของเบราว์เซอร์ = เล่นได้หลังแตะ (SRS §2.2, ADR-01)
- **Alternatives:** ไฟล์ `.mp3` — ต้องโหลดไฟล์ (file:// ได้ด้วย `<audio>` แต่เพิ่มไฟล์โดยไม่จำเป็น) · Notification API — ต้องขออนุญาตและไม่ทำงานบน file://

## R-8 S2 เป็นหน้าของผู้สูงอายุหลังจับคู่ (ถึง FR-04)

- **Decision:** S2 `isStart` = ผู้สูงอายุจับคู่แล้ว · S2 มี 3 สถานะ: `ALERT` (มี `dueSessions`) · `IDLE` (มียา ไม่มีมื้อต้องเตือน: "ยังไม่ถึงเวลากินยา" + เวลามื้อถัดไปของวันนี้) · `EMPTY` (✗5) ·
  S1 สถานะเชื่อมต่อแล้ว → ปุ่ม "หน้าเตือนกินยา" ไป S2 (เหมือน C1 → C2) · S2 มีปุ่ม "การเชื่อมต่อ" ไป S1 (ยกเลิกการจับคู่ อยู่ที่ S1 · §8.5) · เปลี่ยนสถานะด้วย `ctx.subscribe` (เวลาจำลอง + store)
- **Rationale:** ผู้สูงอายุไม่ต้องกดอะไรเพื่อให้หน้าเตือนขึ้น (R8) เพราะ S2 เปิดค้างอยู่แล้ว · ไม่ต้องเพิ่มกลไกใน shell · "มื้อถัดไป" คือข้อความเดียวของสถานะว่าง (feedback ว่าระบบยังทำงาน) ไม่ใช่รายการมื้อของวัน (นั่นคือ S3 ของ FR-04)
- **Alternatives:** hook ทั้งแอปใน shell เปิด S2 เมื่อถึงเวลา — แก้ Foundation (§8.5 ปฏิเสธแนวนี้แล้ว) · รอ S3 ก่อน — ✗5 ไม่มีที่แสดง
- **ส่งต่อ FR-04:** ลบ toast "ยังบันทึกไม่ได้ในรุ่นนี้" (R-9) เมื่อปุ่มทำงานแล้ว · ถ้า S3 เป็นหน้าแรก ให้ S3 `ctx.go('S2')` เมื่อ `dueSessions` ไม่ว่าง และ S2 กลับ S3 เมื่อว่าง

## R-9 ปุ่มบน S2 ก่อน FR-04

- **Decision:** แสดง "กินแล้ว" (`btn--primary btn--xl`) + "ยังไม่กิน" (`btn--secondary btn--xl`) ต่อมื้อ · ถ้ายังไม่มีโมดูล `MedMind.confirm` → กดแล้ว toast "ยังบันทึกไม่ได้ในรุ่นนี้" (feedback ทุกการกระทำ) และไม่เขียนอะไร · มีแล้ว → เรียกตามสัญญา FR-04
- **Rationale:** ✓1 ต้องเห็นปุ่ม (BR-09) · ปุ่มเงียบผิดกติกา feedback · ไม่เขียน `confirmations` เองเพราะเป็นของ FR-04
- **Alternatives:** ซ่อนปุ่มจน FR-04 มา — ไม่ผ่าน ✓1 · เขียนบันทึกยืนยันเองใน S2 — ทำงานของ FR-04 ซ้อน
