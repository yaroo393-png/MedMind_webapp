# Research: แจ้งผู้ดูแล + สถานะรายวัน (005-status)
<!-- เจ้าของ: E (Nichanan Lalua) · ร่างโดย A ตามที่ทีมตัดสิน 23/10/69 · Claude Code /speckit-plan -->

ไม่มีช่อง NEEDS CLARIFICATION เหลือใน spec (clarify 24/10: แถบค้างจนกด "ดูสถานะ") · ข้อด้านล่างคือการตัดสินใจทางเทคนิคที่ spec ปล่อยให้ plan

## R-1 `escalate` = ฟังก์ชันล้วน ทำซ้ำได้ไม่เพิ่ม · แจ้งได้เฉพาะในช่วง [T+15, lateUntil)

- **Decision:** `escalation.escalate(sessions, confirmations, notices, pairingId, now)` → เพิ่ม `UNCONFIRMED` ให้ทุกมื้อที่ `now ≥ at + 15 นาที` และ `now < doseSession.lateUntil(session, sessions)` และไม่มีบันทึกยืนยันของคู่นี้ ผ่าน `addNotice` ·
  ไม่มีอะไรเพิ่ม → คืน **รายการเดิม (ตัวเดิม)** เพื่อให้หน้าจอเขียนเฉพาะเมื่อเปลี่ยน · `sessions` = มื้อของเมื่อวาน + วันนี้ (มื้อดึก T+15 หลังเที่ยงคืน)
- **Rationale:** ADR-06 ทุกหน้ารันกฎ → ผลต้อง idempotent (BR-13, §8.4) · ช่วงสิ้นสุดใช้ `lateUntil` ตัวเดียวกับ FR-03/FR-04 (BR-15 ที่เดียว) · ไม่แจ้งย้อนหลังเมื่อพ้นช่วง (spec Assumptions) ทำให้เปิดหน้าเช้าวันถัดไปไม่มีข้อความเก่าท่วม · **implement 24/10:** มื้อที่ช่วงยืนยันช้าว่าง (23:50 → T+15 = 00:05 = lateUntil) test จับได้ว่าจะไม่ถูกแจ้งเลย → แจ้งได้จนจบวันของ T+15
- **Alternatives:** แจ้งทุกมื้อที่เลย T+15 ไม่จำกัดช่วง — เปิดหน้าวันถัดไปได้ข้อความเก่าหลายรายการที่ทำอะไรต่อไม่ได้ · ตั้งเวลาแยก (timer) ต่อมื้อ — นาฬิกาจำลองกระโดดได้ ต้องคำนวณจากเวลาอยู่ดี (ADR-02)

## R-2 ผู้รันกฎตามเวลา = ตัวรันระดับหน้าเว็บใน `screens/status.js` (ไม่ผูกหน้าจอ)

- **Decision:** `status.js` ลงทะเบียนตัวรัน 1 ตัวต่อหน้าเว็บหลัง shell boot (`DOMContentLoaded` ของ shell ทำงานก่อน เพราะ script โหลดก่อน) · เรียกตอนเริ่ม, เมื่อ `clock.onChange` และ `store.subscribe` ·
  คำนวณจากข้อมูลในหน่วยความจำ → มีข้อความใหม่เท่านั้นจึง `store.reload()` แล้วคำนวณซ้ำก่อน `store.set('notices', …)` · กันเรียกซ้อนด้วยตัวแปร `busy` (reload/set แจ้งผู้ฟังรวมถึงตัวรันเอง)
- **Rationale:** แจ้งได้แม้เปิดแค่แท็บผู้สูงอายุหรือแค่แท็บผู้ดูแล (R6) และไม่ขึ้นกับว่าอยู่หน้าไหน · store เขียนทั้งก้อนลงที่เก็บของเบราว์เซอร์ → แท็บที่ข้อมูลเก่าเขียนทับข้อมูลใหม่ได้ จึง reload ก่อนเขียน (กติกาเดียวกับ handler) · เขียนน้อยครั้ง (1 ครั้งต่อมื้อ) จึงไม่เปลือง
- **Alternatives:** รันใน C3 และ S2 ตาม §8.4 เดิม — ผู้ดูแลอยู่หน้า C2 หรือผู้สูงอายุอยู่ S3 ตอน T+15 → ไม่แจ้ง (ขัด R6) · hook ใน shell — เพิ่มกลไกใน Foundation (ปฏิเสธแบบเดียวกับ §8.5) · reload ทุกครั้งที่ตรวจ — ทุกหน้าวาดซ้ำ 2 เท่าทุกครั้งที่เวลาเปลี่ยน
- **ผลต่อสัญญา:** architecture §8.4 แก้ "ตัวเรียกรวมอยู่ที่ C3 และ S2" เป็นตัวรันระดับหน้าเว็บใน `status.js`

## R-3 แถบค้างจนกด = ฟิลด์ `seenAt` ใน CaregiverNotice (clarify 24/10)

- **Decision:** เพิ่มฟิลด์ `seenAt` (datetime หรือ `null`) · `null` = ผู้ดูแลยังไม่กด "ดูสถานะ"/"รับทราบ" · `escalation.unseen(notices, pairingId)` → รายการที่ยังไม่กด · `escalation.markSeen(notices, pairingId, now)` → ใส่ `seenAt` ทุกรายการที่ยังไม่กดของคู่นี้ (ไม่มี = รายการเดิม)
- **Rationale:** แถบต้องไม่ขึ้นอีก "บนเครื่องนั้น" ทั้งหลังรีเฟรชและในแท็บอื่นของเครื่องเดียวกัน (spec edge) → ต้องอยู่ใน store · MVP มีผู้ดูแล 1 คนต่อคู่ (BR-02) จึงเก็บที่ข้อความได้เลย · ข้อมูลยังเป็นของคู่ → `unpair` ลบด้วย (NFR-10)
- **Alternatives:** จำในหน่วยความจำของหน้า — รีเฟรชแล้วแถบขึ้นใหม่ทั้งหมด · ชุดข้อมูลแยก `noticeSeen` — entity ใหม่ที่ผูกกับข้อความ 1:1 อยู่แล้ว · localStorage ของผู้ดูแลแยก — ผิดชั้นข้อมูล (Data ผ่าน store เท่านั้น)
- **ผลต่อสัญญา:** architecture §6 ERD เพิ่ม `seenAt` (FR-05 R11) · §8.3 เพิ่ม `unseen`, `markSeen`

## R-4 ข้อความแจ้งคำนวณจากชนิด + บันทึกยืนยัน ไม่เก็บตัวข้อความ

- **Decision:** `escalation.noticeText(notice, confirmations)` → `UNCONFIRMED`: "ยังไม่ยืนยันการกินยา" · `CONFIRMED_LATE`: "ยืนยันการกินยาแล้ว เวลา HH:MM" (HH:MM = `confirmedAt` ของบันทึกของคู่+มื้อนั้น · ไม่พบ = "ยืนยันการกินยาแล้ว") · หน้าจอเติม "มื้อ HH:MM · " ข้างหน้า
- **Rationale:** AC ✓6 ต้องเป็นเวลาที่แตะ (08:40) ไม่ใช่เวลาที่ส่ง (ส่งหลังพ้นช่วงยกเลิก) · เวลายืนยันอยู่ในบันทึกยืนยันแล้ว (ค่าคำนวณไม่ใช่ field) · คำอยู่ที่เดียว (architecture §8.1)
- **Alternatives:** เก็บ `confirmedAt` ซ้ำในข้อความ — ข้อมูลซ้ำสองที่ · ใช้ `sentAt` — เวลาไม่ตรง AC ถ้านาฬิกาจำลองเดินระหว่าง 10 วินาที

## R-5 สถานะรายวันใช้ `confirm.statusOf` / `statusLabel` (ส่งต่อจาก 004 R-4)

- **Decision:** `escalation.dailyStatus(sessions, confirmations, pairingId, now)` → `[{ sessionKey, at, medicationIds, status, confirmedAt, label }]` เรียงตามเวลา · `status`/`label` จาก `confirm` · ไม่มีมื้อ = `[]` ·
  `escalation.noticesOf(notices, pairingId, now)` → ข้อความของคู่นี้ที่ `sentAt` เป็นวันนี้ ล่าสุดก่อน
- **Rationale:** ผู้ดูแลและผู้สูงอายุเห็นคำเดียวกัน (SC-004) · กรองด้วย `pairingId` ในฟังก์ชันล้วน → test NFR-04 ได้
- **Alternatives:** C3 เรียก `confirm` เองทีละมื้อแบบ S3 — กฎ "เรียง/กรองคู่" หลุดไปอยู่ในหน้าจอ test ไม่ได้

## R-6 หน้า C3 + แถบแจ้งบนทุกหน้าผู้ดูแล

- **Decision:** `screens/status.js` ลงทะเบียน C3 (`isStart` = `canAccess`) และ export `MedMind.status.noticeBanner(ctx)` · C2 (B) เพิ่ม 1 บรรทัดวางแถบบนสุดใน `draw()` · แถบ = `.banner--warn` รายการ "มื้อ HH:MM · ข้อความ" + ปุ่ม `btn--secondary` "ดูสถานะ" (C2 → `markSeen` + ไป C3) หรือ "รับทราบ" (บน C3 → `markSeen`) ·
  C1 ไม่ต้องมี (ยังไม่จับคู่ = ไม่มีข้อความให้เห็น · NFR-04)
- **Rationale:** C2 วาดใหม่ทุกครั้งที่ store เปลี่ยนโดยเก็บร่างและโฟกัสไว้ (ตรวจแล้ว) → แถบขึ้นโดยไม่ลบสิ่งที่กรอก (spec edge) · ใช้ component ที่มีแล้ว ไม่มีคู่สีใหม่
- **Alternatives:** แถบใน header ของ shell — แก้ Foundation และ shell ต้องรู้เรื่อง FR-05 · toast ของ shell — หายใน 4 วินาที (ผู้ใช้เลือกแถบค้าง)

## R-7 หน้าแรกของผู้ดูแล: C3 เมื่อมียา · C2 เมื่อยังไม่มียา

- **Decision:** C2 `isStart` = จับคู่แล้ว **และ** ยังไม่มียาของคู่นี้ · C3 `isStart` = จับคู่แล้ว (ลงทะเบียนหลัง C2 → เป็นหน้าแรกเมื่อ C2 ไม่ใช่) · C1 หลังจับคู่ใช้ `nextScreenId()` เดิม → ได้ C2 (ยังไม่มียา) · C2 เพิ่มปุ่มรอง "สถานะวันนี้" → C3 · C3 มีปุ่มรอง "ยาของผู้สูงอายุ" → C2 · C3 สถานะว่าง ✗4 มีปุ่มเดียวกัน
- **Rationale:** คำถามที่ 2 ของผู้ดูแลคือสถานะ → หน้าแรกเมื่อมียาแล้ว · ก่อนมียาไม่มีสถานะให้ดู ต้องเพิ่มยาก่อน (FR-02) · ไม่มีหน้าใหม่ ไม่แก้ shell
- **Alternatives:** C3 เป็นหน้าแรกเสมอ — หลังจับคู่เห็น "ยังไม่มีมื้อยาวันนี้" ก่อนทุกครั้ง ต้องกดอีกขั้น · คง C2 เป็นหน้าแรก — ผู้ดูแลต้องกดไปดูสถานะทุกครั้ง

## R-8 ฝั่งผู้สูงอายุหลังมี FR-05 (ส่งต่อจาก 004 R-5)

- **Decision:** `reminder.js` ลบ `NOT_READY_TEXT` และทางที่ไม่มี `MedMind.escalation` (index.html โหลด escalation.js เสมอแล้ว) · ถ้าไม่มี → `console.error` ตอนโหลดเหมือนโมดูลอื่น · `notifyCaregiver` เรียก `addNotice` แล้ว toast "แจ้งลูกหลานแล้ว" ตามเดิม
- **Rationale:** spec R14 · ทางสำรองที่ไม่มีวันถูกใช้คือโค้ดตาย
- **Alternatives:** คงทางสำรองไว้ — โค้ดที่ test ไม่ได้และข้อความที่ไม่จริงแล้ว
