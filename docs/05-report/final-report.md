## 1. ปัญหาและผู้ใช้ (จาก M1 · `docs/01-charter/charter.md`)

ผู้สูงอายุที่กินยาประจำ **จำไม่ได้ว่ามื้อนี้กินยาแล้วหรือยัง** เพราะนาฬิกาปลุกและกล่องแบ่งยาเตือนได้แต่ไม่บันทึก · ลูกหลานที่ทำงานต้อง **โทร/LINE ถามประมาณ 5–6 ครั้งต่อสัปดาห์** และติดประชุมก็โทรไม่ได้

หลักฐานชั้น B: สัมภาษณ์ผู้ใช้จริง 3 คนทางโทรศัพท์ 4/9/69 (`evidence/interviews-2569-09-04.md`) — ผู้สูงอายุ 68 ปี (ปิดเสียงเตือนแล้วลืม) · ลูกหลาน 35 ปี ("อยากให้แจ้งเฉพาะตอนแม่ยังไม่ยืนยัน") · ผู้สูงอายุ 65 ปี (ไม่สะดวกสมัครบัญชี อยากให้ลูกตั้งค่าให้)

ระบบตอบ 2 คำถาม: **ผู้สูงอายุ** "มื้อนี้ต้องกินยาอะไร และกินแล้วหรือยัง?" · **ผู้ดูแล** "วันนี้กินยาครบทุกมื้อหรือยัง โดยไม่ต้องโทรถาม?"

**PDPA:** NFR-04 ผู้ดูแลเห็นเฉพาะคู่ของตน · NFR-05 ไม่เชื่อมต่อก่อนยินยอม · NFR-09 ไม่เก็บเลขบัตร/HN/ที่อยู่ ไม่ส่งข้อมูลออกนอกเครื่อง · NFR-10 ยกเลิกจับคู่แล้วข้อมูลเหลือ 0 ·

## 3. การออกแบบ (จาก M2 · `docs/03-design/`)

- **สถาปัตยกรรม:** monolith 3 ชั้นรันในเบราว์เซอร์ ไม่มี server — Presentation (6 หน้าจอ) → Logic (8 โมดูลฟังก์ชันล้วน รับเวลาจาก clock) → Data (ที่เก็บของเบราว์เซอร์) · ADR 8 ข้อพร้อมทางเลือกที่ปฏิเสธ
  เช่น ADR-01 เว็บแอปเตือนเฉพาะขณะเปิดหน้า (ปฏิเสธแอป native — เกินเวลาและเกณฑ์ M3 ขอเว็บ · Web Push — ต้องมี server) · ADR-02 นาฬิกาจำลอง ทำให้ทดสอบ T+15 ได้ทันที
- **Diagram (Mermaid · ติดป้าย FR):** Use Case 7 ข้อ · Sequence 3 รูป (เตือน→ยืนยัน→แจ้ง · เพิ่มยา · จับคู่) · State ของมื้อยา · ERD 9 entity · user flow 4 งาน + แผนที่หน้าจอ
- **Data model (tech-agnostic):** SENIOR, CAREGIVER, INVITE_CODE, PAIR_ATTEMPT, PAIRING, MEAL_TIMES, MEDICATION, DOSE_CONFIRMATION, CAREGIVER_NOTICE · ทุกระเบียนผูก `pairingId` → ยกเลิกจับคู่ลบได้ครบ ·
  ค่าที่คำนวณได้ (เวลาเตือน รอบเตือน สถานะ) ไม่เก็บเป็น field
- **UI:** design system (tokens · components · contrast ทุกคู่สี ≥ 5.71:1) · wireframe low-fi 6 หน้าจอ · 1 หน้าจอ 1 ปุ่มหลัก · ผู้สูงอายุไม่ต้องพิมพ์ ไม่มีบัญชี
