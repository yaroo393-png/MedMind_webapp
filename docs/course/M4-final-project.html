01 Weighting / การกระจายคะแนน

โปรเจกต์ = 30% ของวิชา กระจายอย่างไรThe project is 30% of the course — here's the split

น้ำหนักคะแนนไต่ขึ้นเรื่อย ๆ เพราะ M1–M2 คือ “วัตถุดิบ” ของ M3 — prototype ที่ดีเกิดได้ต่อเมื่อเอกสารก่อนหน้าแน่น การให้คะแนนแบบนี้จึงให้รางวัลทีมที่ปรับปรุงงานตาม feedback ต่อเนื่อง

The weight rises toward the end because M1–M2 feed M3 — a strong prototype is only possible if the earlier documents were solid. This rewards teams that keep improving on feedback.

04 Fairness / ส่วนร่วมรายคน

คะแนนส่วนร่วมรายคน (แบบ “ลงอย่างเดียว”)Individual contribution (down-only)

โปรเจกต์เป็นคะแนนกลุ่ม แต่เราปกป้องคนที่ทำงานจริง — ทุกคนเริ่มที่ ×1.0 และปรับ ลดได้เท่านั้น เฉพาะเมื่อมีหลักฐานชัด

The project is a team grade, but we protect the members who do the work — everyone starts at ×1.0 and the factor can only go down, and only with clear evidence.

คะแนนโปรเจกต์รายคน = คะแนนทีม × FactorYour project mark = team score × factor

FactorระดับLevelความหมายMeaning

0.70มีส่วนร่วมบางส่วนPartial contributorงานใน GitHub บางเบา/กระจุกท้าย และชี้แจงแล้วThin GitHub work / clustered at the end, after a chance to explain
0.40แทบไม่มีส่วนร่วม (ghost)Ghost memberไม่มีร่องรอยงานที่ตรวจสอบได้ตลอดโปรเจกต์No traceable contribution across the whole project

08 Appendix / ภาคผนวก

ภาคผนวก — หน้าตา clickable prototype จริงเป็นแบบนี้Appendix — what a real clickable prototype looks like

นี่คือ prototype จริงจากงานวิจัย CoffeeAI — Coffee Metabolomics Database ของอาจารย์ (research→teaching) เป็น HTML/CSS ล้วน 9 หน้าจอ ไม่มี server — คลิกที่จะส่งข้อมูลจริงเป็นแค่ของประกอบ ทุกหน้าจอกำกับว่า cover FR/NFR ข้อไหน และจัดกลุ่มตาม user journey นี่คือระดับที่ M3 ต้องการ

A real prototype from the instructor's CoffeeAI — Coffee Metabolomics Database research (research→teaching). It is nine pure HTML/CSS screens, no server — clicks that would submit data are decorative. Every screen is tagged with the FR/NFR it covers, grouped by user journey. This is the level M3 asks for.

รูป A.1 — หน้า Index: สารบัญหน้าจอ บอกว่าแต่ละหน้า cover FR/NFR ข้อไหน + จัดตาม journeyFig A.1 — Index: a screen map showing which FR/NFR each screen covers, grouped by journey

รูป A.2 — หน้า Sample library (cover FR-10): มี stat cards, ตัวกรอง, ตารางข้อมูล — เป็นข้อมูลตัวอย่าง (mock) ไม่ได้ต่อฐานข้อมูลจริงFig A.2 — Sample library (covers FR-10): stat cards, filters, a data table — mock data, not wired to a real database

สังเกต 4 อย่างจากตัวอย่างนี้ (คือสิ่งที่ M3 ให้คะแนน)Four things to notice (this is what M3 rewards)

  • ทุกหน้าจอกำกับ FR/NFR — ชี้ได้ว่าหน้านี้ = requirement ข้อไหน (แถบ "Covers:" บนสุด)Every screen is tagged with its FR/NFR — you can point: this screen = which requirement (the "Covers:" bar on top)
  • ไม่มี backend/DB จริง — ข้อมูลเป็น mock, ปุ่มที่จะบันทึกจริงเป็นของประกอบ (ตรงกับ "clickable prototype" ของ M3)No real backend/DB — data is mock, submit buttons are decorative (exactly M3's "clickable prototype")
  • จัดตาม user journey — เดินตาม flow ของผู้ใช้จริง (QC/Cupping Lead) ไม่ใช่หน้าจอลอย ๆGrouped by user journey — follows a real user's flow (QC/Cupping Lead), not loose screens
  • design system เดียวทั้งชุด — สี/ฟอนต์/องค์ประกอบเหมือนกันทุกหน้า (ต่อยอดจาก design system ใน M2)One design system throughout — same colors/type/components on every screen (extends the M2 design system)
สเกลของ นศ. ทำได้เล็กกว่านี้Your scale can be smaller ตัวอย่างนี้มี 9 หน้าจอเพราะเป็นระบบจริง — โปรเจกต์ นศ. ขอแค่ ครบทุก Must FR (มัก 3–5 หน้าจอ) คลิกเดิน flow ได้ก็พอ This example has nine screens because it is a real system — your project only needs to cover every Must FR (often 3–5 screens) with a clickable flow.
