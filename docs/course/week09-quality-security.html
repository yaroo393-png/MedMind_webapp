intro2se-ch8-quality-security.fig / Quality attributes
PART 1: WHAT QUALITY MEANS

Quality is several attributes — and each is checkable

Reliability

It keeps working

Same input → same correct result, even on a bad day. Checked by tests.

Usability

People can use it

Clear, forgiving, learnable. Checked by watching a real user try it.

Maintainability

Easy to change

Readable code future-you can edit. Checked by reviews & linters.

Security

It protects data

Only the right people see the right data. Checked by thinking like an attacker.

Performance

Fast enough

Responds within the NFR budget. Checked by measuring, not guessing.

The point

You check, not hope

Every attribute traces back to an NFR in your SRS — and to a way to verify it.

In plain terms

Quality isn't one thing — it's a checklist, like judging a restaurant: taste, speed, cleanliness, price. Each is real, and each is checked a different way.

NEW in 2023
Why it changed

The 2023 edition (replacing 2011) renamed Usability and Portability and added Safety, because software now runs cars, medical devices and AI systems. Each characteristic in your SRS becomes an NFR you can check.

Source: ISO/IEC 25010:2023 Product quality model, Edition 2 (iso.org/standard/78176.html). Sommerville 9e Ch24 describes the earlier 2011 model.

intro2se-ch8-quality-security.fig / Review & static checks
PART 1: CHEAP, POWERFUL QUALITY TOOLS

Code review & the linter catch problems early

Human

Code review

A teammate reads your code before it reaches main — this is what a Pull Request is for (Ch6). Catches logic bugs, unclear names, missing cases, and spreads knowledge across the team.

Automatic

Linter / static analysis

A tool that reads the code without running it and flags style, unused variables, likely bugs, risky patterns. Fast, consistent, runs on every commit.

In plain terms

A linter is spell-check for code; a code review is a classmate proof-reading your essay. Neither is optional on a real team — and both make AI-generated code far safer to keep.

intro2se-ch8-quality-security.fig / Cost of fixing defects
PART 1c: WHY CHECK EARLY (BOEHM)

The later you catch a defect, the more it costs

Illustrative scale — a bug caught in review/test is cheap; the same bug in production is not

After Boehm (1981) Software Engineering Economics. This is why reviews (here) and unit tests (Ch7) pay for themselves — they move the catch leftward.

In plain terms

A typo you catch while writing costs nothing; the same typo found after the book is printed means a reprint. Bugs are identical — catching them early, in a review or a test, is why both are worth the time.

intro2se-ch8-quality-security.fig / The big three
PART 2: SECURITY YOU CAN APPLY TODAY

Three habits that stop most beginner mistakes

#1

Validate input

Never trust data from the user or the browser. Check type, length and range on the server, before you use or store it.

#2

Access control

A logged-in user may see only their own data. Check “who are you, and is this yours?” on every request.

#3

No secrets in the repo

Passwords, API keys, tokens never go in the code or Git history. Use .env + .gitignore (Ch6).

In plain terms

Picture a shop: check what comes through the door (validate input), only staff can open the till (access control), and never tape the keys to the door (no secrets in the repo).

intro2se-ch8-quality-security.fig / A vulnerability you can find today
PART 2: TRUSTING THE CLIENT = THE CLASSIC HOLE

If the user can change the id, they can read your data

Wrong: The server trusts an id from the URL

# anyone logged in can swap the number GET /api/notes?user_id=1042 def get_notes(user_id): return db.notes.where(owner=user_id) # ...whose id is this? nobody checked.

Change 1042 to 1043 → you're reading someone else's notes. This is IDOR — broken access control.

Right: Use the identity from the session

# id comes from WHO is logged in GET /api/notes def get_notes(session): me = session.user # trusted return db.notes.where(owner=me.id)
The rule

Never decide “whose data” from something the user can edit. Derive it from the authenticated session.

intro2se-ch8-quality-security.fig / Privacy & PDPA
PART 3: A LEGAL DUTY, NOT JUST GOOD MANNERS

Personal data comes with responsibilities

Consent

Ask first

Collect personal data — schedules, notes, messages, faces — only with the person's informed consent, for a stated purpose.

Minimise

Collect the least

If the feature doesn't need it, don't store it. Less data = less risk and less to protect.

Protect

Guard & honour rights

Secure it, and let people see, correct or delete their data. This is PDPA — Thai law since 2022.

For your project

Use fake / seed data in the prototype. Real personal data belongs nowhere near a student repo — and never in Git history.

intro2se-ch8-quality-security.fig / Concept check 3
CONCEPT CHECK 3: PDPA

Consent, minimise, or protect?

SituationPrinciple
A note-taking app asks to read your whole contact list, but no feature uses it.Minimise
An app stores photos of users' faces without saying what they are for.Consent (and state the purpose)

Remember

PDPA (B.E. 2562, fully in force 2022): consent before collecting, minimise what you keep, protect it and honour the owner's rights.

intro2se-ch8-quality-security.fig / Case: CareFlow OPD
CASE: CAREFLOW OPD, A WHAT-IF ON A STUDENT PROJECT

Four Ch8 failures in one small system

Access control (IDOR)

Change the number, see another patient

The server trusted the appointment id in the link. Fix: take the patient from the login session and check the appointment is theirs, for viewing and for cancelling.

PDPA: minimise, protect

Health data is sensitive

Symptoms are health data, a sensitive category under PDPA that needs explicit consent. Does the booking page need symptoms at all? Show the least, protect the rest.

Quality: check, don't hope

"All tests passed"

The tests only tried honest users. Add the attacker's case: patient A asks for patient B's appointment, and the system must refuse.

No secrets in the repo

A password in a public repo

Anyone could read config.js. Revoke the password and keep secrets in .env listed in .gitignore. Deleting the line is not enough: Git history keeps it.

The lesson

You don't need a giant company to break every rule in Ch8. A student-sized system with real patients needs the big three and PDPA from day one.

What-if scenario built on a student project idea (Must FRs: book, view, cancel appointments). It does not describe any team's actual prototype. PDPA B.E. 2562, Section 26: health data is sensitive personal data.
