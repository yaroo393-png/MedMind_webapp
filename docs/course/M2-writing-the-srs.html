Not Just a “Wishlist of Features”

คู่มือแปลง “ปัญหา” จาก M1 ให้กลายเป็น ข้อกำหนดความต้องการ (SRS) ที่ชัด วัดผลได้ และให้ AI ลงมือสร้างต่อได้ทันที — ทีละ FR ทีละ NFR อย่างเป็นระบบ A guide to turning the problem from M1 into a Software Requirements Specification that's clear, testable, and ready for AI to build from — one FR and one NFR at a time.

ประโยคเดียวที่ต้องจำ requirement ที่ดีไม่ใช่ “สิ่งที่อยากได้” แต่คือ ข้อตกลงที่ทดสอบได้ ถ้าเขียนจนใครมาอ่านก็เข้าใจตรงกัน และรู้ว่า “เสร็จ” หน้าตาเป็นยังไง — AI จะสร้างของถูกตัว ถ้าเขียนกำกวม ต่อให้ AI เก่งแค่ไหน ก็สร้างผิดเรื่อง One sentence to remember: a good requirement isn't “what you want” — it's a testable agreement. Write it so any reader understands the same thing and knows what “done” looks like, and the AI builds the right thing. Write it vaguely and no amount of AI skill builds the right thing.

01 Mindset / กรอบความคิด

SRS คืออะไร และทำไมต้องเสียเวลาเขียนWhat an SRS is — and why it's worth the time

ใน M1 คุณเลือก “ปัญหา” และรู้ว่าใครคือผู้ใช้ ตอนนี้คำถามเปลี่ยนเป็น “แล้วระบบต้องทำอะไรได้บ้าง” SRS (Software Requirements Specification) คือเอกสารที่ตอบคำถามนี้แบบตรวจสอบได้ — เป็นสะพานระหว่าง “ไอเดียในหัว” กับ “โค้ดที่รันได้”

In M1 you chose a problem and named your users. The question now becomes “so what must the system actually do?” An SRS (Software Requirements Specification) answers that in a checkable way — it's the bridge between the idea in your head and code that runs.

ไม่มี SRSWithout an SRS

“ทำแอปจองคิวร้านกาแฟนะ” → แต่ละคนในทีมจินตนาการคนละแบบ โค้ดชนกัน AI สร้างฟีเจอร์ที่ไม่มีใครขอ“Let's build a coffee-shop queue app” → each teammate imagines something different, code collides, the AI builds features nobody asked for.

ถึงเวลาส่ง ถึงรู้ว่า “ไม่ตรงที่คิด” แต่แก้ไม่ทันแล้วBy submission day you discover it's “not what we meant” — too late to fix.

มี SRSWith an SRS

“FR-01 ผู้ใช้จองคิวได้, FR-02 เห็นคิวปัจจุบัน, NFR-01 โหลด < 3 วิบนมือถือ” ทุกคนเห็นภาพเดียวกัน“FR-01 user reserves a slot, FR-02 sees the current queue, NFR-01 loads in < 3s on mobile.” Everyone sees the same picture.

แต่ละ requirement รู้ว่า “เสร็จ” หน้าตายังไง ทดสอบได้ แบ่งงานได้Each requirement has a testable definition of done, so work can be split and checked.

3 สิ่งที่ SRS ให้คุณThree things an SRS buys you
  • ภาษากลาง ทีม อาจารย์ ผู้ใช้ และ AI อ่านแล้วเข้าใจตรงกัน ไม่ต้องเดาA shared language: team, instructor, users, and AI all read it the same way — no guessing.
  • นิยามของคำว่า “เสร็จ” ทุก requirement บอกล่วงหน้าว่าจะทดสอบยังไงA definition of “done”: every requirement says up front how it will be tested.
  • แผนที่แบ่งงาน FR/NFR แต่ละตัวกลายเป็นงานที่มอบหมายและติดตามได้A work map: each FR/NFR becomes a task you can assign and track.
SRS ไม่ใช่นิยายAn SRS is not an essay อย่าเขียนเป็นเรียงความยาว ๆ SRS ที่ดีคือ รายการข้อสั้น มีรหัส วัดผลได้ เขียนสิ่งที่ระบบต้อง “ทำ” (What) ไม่ใช่ “ทำยังไง” (How) — เรื่อง How เก็บไว้ตอนออกแบบ (M3) Don't write long prose. A good SRS is a list of short, ID'd, testable statements. Say what the system must do (the What), not how it does it (the How) — the How belongs to design (M3).

02 Anatomy / กายวิภาค

ข้างใน SRS มีอะไรบ้างWhat's inside an SRS

มาตรฐาน IEEE 830 / ISO 29148 มีหัวข้อเยอะมาก แต่วิชานี้เก็บ SRS แบบเบา 7 ส่วน (ตรงกับบทที่ 4 ของวิชา) พอครบ 7 ส่วนนี้ ทีมและ AI ก็เริ่มสร้างได้ และข้อสำคัญคือ ส่วนที่เว้นว่างถือว่าตก

IEEE 830 / ISO 29148 list many sections, but this course keeps a lightweight 7-part SRS (matching the course's Chapter 4). With these seven in place, your team — and the AI — can start building; and note: an empty section still counts as a failed section.

ส่วนSection ตอบคำถามว่าAnswers the question
1. จุดประสงค์ & ขอบเขตPurpose & scope ระบบนี้แก้ปัญหาอะไร ทำอะไรบ้าง — ดึงตรงจาก Problem Brief ของ M1What problem it solves and what it does — pulled straight from your M1 Problem Brief.
2. ผู้มีส่วนได้เสีย (Stakeholders)Stakeholders ใครเกี่ยวข้องบ้าง อย่างน้อย 3 คน/ฝ่าย เช่น ผู้ใช้ ผู้กำหนดกติกา เจ้าของข้อมูล ระบบภายนอกAt least 3 — e.g. the user, whoever sets the rules, the data owner, an external system.
3. Functional Requirements (FR) ระบบต้องทำอะไรได้ — เขียนเป็น user story + acceptance มีรหัส FR-01, FR-02…What the system must do — written as user stories with acceptance criteria, each ID'd FR-01…
4. Non-Functional Requirements (NFR) ระบบต้อง “ดี” แค่ไหน — เร็ว ปลอดภัย รองรับกี่คน ต้องมีเรื่องความเป็นส่วนตัว/PDPA อย่างน้อย 1 ข้อ มีรหัส NFR-01…How well — speed, security, capacity — with at least one privacy/PDPA line, each ID'd NFR-01…
5. ชื่อ Use CaseUse case names ระบุ “ชื่อ” use case หลัก ๆ ไว้ (ตัวไดอะแกรมค่อยวาดใน M3 Modeling)List the main use case names (the diagrams themselves come in M3 Modeling).
6. Out-of-ScopeOut-of-scope สิ่งที่ ตั้งใจจะไม่ทำ เทอมนี้ — สัญญากับทีมเองว่าจะไม่ปล่อย scope บวมWhat you deliberately won't build this term — a promise to your team against scope creep.
7. บันทึกการใช้ AIAI-use log ใช้ AI ช่วยตรงไหน ตรวจ/แก้อะไรบ้าง — วิชานี้ถือว่า ขาดไม่ได้ (AI ร่างได้ แต่คนเซ็นรับผิดชอบ)Where AI helped and what you verified/changed — mandatory here (AI may draft, a person signs off).
เท่านี้ก่อน อย่าเพิ่งใส่Keep it this size — don't add yet ยังไม่ต้องมี database schema, API, สถาปัตยกรรม หรือหน้าจอ — พวกนั้นคือ M3 Design SRS ตอบแค่ “ระบบต้องทำอะไร” และ “ดีแค่ไหน” เท่านั้น (acceptance criteria อยู่แนบใต้ FR แต่ละข้อ ดู section 7) No database schema, APIs, architecture, or screens yet — those are M3 Design. The SRS answers only “what must it do” and “how well” (acceptance criteria sit beneath each FR — see Section 7).
อ้างอิงSource โครง 7 ส่วนนี้ยึดจากเอกสารประกอบการสอน Intro2SE บทที่ 4 (Requirements) ซึ่งเก็บ subset แบบเบาของ IEEE Std 830-1998 / ISO/IEC/IEEE 29148:2018 This 7-part structure follows the Intro2SE Chapter 4 (Requirements) teaching notes — a lightweight subset of IEEE Std 830-1998 / ISO/IEC/IEEE 29148:2018.

03 Flow / ลำดับการทำงาน

จากปัญหา สู่ requirement — ทำตามลำดับFrom problem to requirements — in order

อย่าเริ่มจากการนั่งลิสต์ฟีเจอร์มั่ว ๆ ให้เดินตามเส้นด้ายจาก M1 ทีละสเต็ป requirement ทุกตัวต้องสาวกลับไปถึง “ปัญหา” ได้

Don't start by brainstorming random features. Walk the thread from M1 one step at a time — every requirement must trace back to the problem.

ปัญหา (M1)problem (M1)→ ผู้ใช้ & งานที่เขาทำusers & their jobs→ ฟีเจอร์features→ FR / NFR→ acceptanceacceptance
  1. เขียน “งาน” ของผู้ใช้ (Jobs)List the users' jobsผู้ใช้แต่ละบทบาทมาที่ระบบเพื่อ “ทำอะไรให้สำเร็จ” เช่น ลูกค้าอยากจองคิวโดยไม่ต้องต่อแถวFor each role, what are they trying to get done? e.g. a customer wants to reserve a slot without standing in line.
  2. แปลงงานเป็นฟีเจอร์Turn jobs into featuresแต่ละงานต้องมีฟีเจอร์รองรับ “จองคิว” → ฟีเจอร์เลือกเวลา + ยืนยัน + ดูสถานะEach job needs features. “reserve a slot” → pick a time + confirm + view status.
  3. แตกฟีเจอร์เป็น FRBreak features into FRsฟีเจอร์หนึ่งอาจเป็นหลาย FR แต่ละ FR เป็นพฤติกรรมเดียวที่ทดสอบได้ ให้รหัส FR-01, FR-02…One feature may be several FRs. Each FR is a single, testable behavior. Give IDs FR-01, FR-02…
  4. ระบุ NFR ที่จำเป็นAdd the NFRs that matterถามว่า “ต้องเร็วแค่ไหน ปลอดภัยแค่ไหน รองรับกี่คน” เฉพาะที่สำคัญกับปัญหาจริงAsk “how fast, how safe, how many users” — only the ones that matter to the real problem.
  5. เขียน acceptance ให้ทุก FR หลักWrite acceptance for every core FRอย่างน้อยทุก FR ที่เป็น MVP ต้องมี Given–When–Then อย่างน้อย 1–2 ฉากAt minimum, every MVP FR gets 1–2 Given–When–Then scenarios.
กับดักที่พบบ่อยCommon trap นักศึกษามักเริ่มจาก “อยากได้หน้าจอสวย ๆ” หรือ “อยากใช้ React” — นั่นคือ solution ไม่ใช่ requirement ให้ถอยกลับมาถามว่า “ผู้ใช้ต้องทำอะไรให้สำเร็จ” ก่อนเสมอ Students often start from “I want a pretty screen” or “I want to use React” — that's a solution, not a requirement. Step back and ask “what must the user accomplish?” first.

04 Functional / FR

เขียน Functional Requirement ที่ดีWrite a good Functional Requirement

ในวิชานี้ ทุก requirement ต้องผ่าน “4 ประตูคุณภาพ (quality gates)” ก่อนรับเข้า SRS — นี่คือเกณฑ์เดียวกับที่อาจารย์ใช้ให้คะแนน (จากบทที่ 4 ของวิชา อิงหลัก INVEST)

In this course, every requirement must pass four quality gates before it enters the SRS — the same bar used for grading (from the course's Chapter 4, grounded in INVEST).

  1. มี role ที่มีชื่อจริง (ไม่ใช่คำว่า “user”)A named role — not the word “user”ระบุผู้มีส่วนได้เสียเจาะจง เช่น “นักศึกษา” “พนักงาน” ไม่ใช่ “ผู้ใช้” ลอย ๆName a specific stakeholder — “a student,” “a staff member” — not a vague “user.”
  2. มี benefit (ส่วน “เพื่อ…/so that”)States a benefit (the “so that” clause)บอกว่าทำไปเพื่ออะไร ถ้าไม่มี benefit มักเป็นฟีเจอร์ที่เดาเอา ไม่ใช่ need จริงSay why. A story with no benefit is usually a guessed feature, not a real need.
  3. acceptance วัดได้ (ตัวเลข / สถานะ / yes-no)Measurable acceptance (a number / state / yes-no)ต้องเขียน Given–When–Then ได้ ถ้าสองคนเถียงกันได้ว่า “ผ่านหรือยัง” แปลว่ายังไม่วัดได้You can write a Given–When–Then. If two people can disagree whether it's met, it isn't measurable yet.
  4. เล็กพอสำหรับ MVP (ราว 3–5 FR)Small enough for an MVP (~3–5 FRs)ถ้าใหญ่เกินไป ให้แตกเป็นหลายเรื่อง หนึ่ง story = หนึ่งพฤติกรรมที่ทดสอบได้If it's too big, split it. One story = one testable behavior.
อ้างอิงSource 4 ประตูคุณภาพ จากเอกสารประกอบการสอน Intro2SE บทที่ 4 (§4.5 User Stories & Acceptance Criteria) อิงเกณฑ์ INVEST (Bill Wake) สำหรับ user story ที่ดี The four gates come from the Intro2SE Chapter 4 teaching notes (§4.5, User Stories & Acceptance Criteria), grounded in the INVEST criteria (Bill Wake) for a good user story.

ภาคผนวก — 9 คุณสมบัติตามมาตรฐาน (อ้างอิงเชิงลึก)Appendix — the 9 standard characteristics (deeper reference)

ถ้าอยากลงลึก มาตรฐาน ISO/IEC/IEEE 29148:2018 ระบุคุณสมบัติของ requirement รายข้อไว้ 9 ข้อ 4 ประตูข้างบนคือเวอร์ชันย่อที่ใช้จริงในชั้นเรียน ส่วน 9 ข้อนี้คือฉบับเต็มของมาตรฐาน

For depth, ISO/IEC/IEEE 29148:2018 lists nine characteristics of an individual requirement. The four gates above are the classroom short form; these nine are the standard's full set.

คุณสมบัติCharacteristic หมายความว่าMeaning
Necessary
จำเป็นnecessary		ระบุความสามารถที่ขาดไม่ได้ ถ้าตัดออกระบบจะบกพร่อง — กันฟีเจอร์เกิน (gold-plating)States a capability that, if removed, leaves a deficiency — guards against gold-plating.
Appropriate
เหมาะกับระดับappropriate		รายละเอียดเหมาะกับระดับของระบบ ไม่ลงลึกเรื่องวิธีทำ (design) เกินความจำเป็นThe level of detail suits the level of the system — not diving into design/how.
Unambiguous
ไม่กำกวมunambiguous		ตีความได้ทางเดียว เลี่ยงคำลอย ๆ เช่น “ง่าย” “เร็ว” “เหมาะสม”Can be interpreted only one way — avoid floaty words like “easy,” “fast,” “appropriate.”
Complete
ครบถ้วนในตัวcomplete		ระบุทุกอย่างที่จำเป็นครบในข้อเดียว ไม่มี “TBD” หรือเงื่อนไขที่หายไปStates all it needs on its own — no “TBD,” no missing conditions.
Singular
ข้อเดียวsingular		ระบุ “ความสามารถเดียว” ถ้ามี “และ” เชื่อม 2 การกระทำ มักต้องแยกเป็น 2 FRStates a single capability — an “and” joining two actions usually means two FRs.
Feasible
ทำได้จริงfeasible		ทำได้ภายในข้อจำกัดด้านเวลา ต้นทุน และเทคนิคของโปรเจกต์Achievable within the project's time, cost, and technical constraints.
Verifiable
ตรวจสอบได้verifiable		พิสูจน์ได้ว่าทำสำเร็จ ด้วยการทดสอบ/ตรวจ/วิเคราะห์ — เขียน Given–When–Then ได้Provable by test/inspection/analysis — you can write a Given–When–Then for it.
Correct
ตรงความต้องการcorrect		สะท้อนความต้องการจริงของผู้ใช้อย่างถูกต้อง สาวกลับถึงปัญหาได้Accurately represents the real user need — traceable back to the problem.
Conforming
ตรงรูปแบบconforming		เขียนตามรูปแบบ/ถ้อยคำมาตรฐานที่ตกลงกัน เช่น ใช้ “ระบบต้อง (shall)”Follows the agreed template/wording — e.g. uses “the system shall.”

The same set appears in SWEBOK v4 (Software Requirements KA) and Sommerville, Software Engineering — both in the course folder.

สูตรเขียน FRAn FR template

Template [รหัส] ระบบต้องอนุญาตให้ [บทบาท] สามารถ [การกระทำ] เพื่อ [ผลลัพธ์/คุณค่า] [ID] The system shall let [role] [do action] so that [outcome/value].
รูปแบบหลักของวิชาThe course's primary format วิชานี้ใช้ user story เป็นรูปแบบหลักของ FR ตลอดเทอม: “ในฐานะ «บทบาท» ฉันต้องการ «เป้าหมาย» เพื่อ «คุณค่า»” แล้วแนบ acceptance แบบ Given–When–Then ข้างใต้ สูตร “ระบบต้อง (shall)” ข้างบนใช้ได้เช่นกัน (นิยมกับ NFR/ระดับระบบ) แต่ให้ถือ user story เป็นค่าเริ่มต้น — ดูวิธีเขียนใน section 5 The course uses the user story as the primary FR format all term: “As a «role», I want «goal», so that «benefit»,” with Given–When–Then acceptance beneath. The “shall” template above is also valid (common for NFRs / system level), but treat the user story as the default — see Section 5.

FR ที่ดีA strong FR

05 Stories / เล่าจากมุมผู้ใช้

User Story กับ Use Case ใช้เมื่อไหร่User stories vs use cases — when to use which

ทั้งสองอย่างช่วยให้ requirement เล่าจาก “มุมของผู้ใช้” ไม่ใช่มุมของระบบ ในวิชานี้เราใช้ User Story เป็นหลัก และเขียน Use Case เฉพาะ flow ที่ซับซ้อน

Both keep requirements told from the user's side, not the system's. In this course we lead with user stories, and write a use case only for the complex flows.

User Story

ประโยคสั้นจากมุมผู้ใช้A short sentence from the user

ในฐานะ [บทบาท] ฉันต้องการ [ทำอะไร] เพื่อ [ได้คุณค่าอะไร] As a [role] I want [action] so that [value].

เช่น “ในฐานะลูกค้า ฉันต้องการจองคิวล่วงหน้า เพื่อไม่ต้องยืนรอหน้าร้าน”e.g. “As a customer, I want to reserve a slot ahead of time, so that I don't stand and wait.”

เหมาะกับ backlog ทำงานเร็ว จับคู่กับ FR ได้ 1:1 หรือ 1:หลายGreat for a backlog, fast, maps to FRs 1:1 or 1:many.

Use Case

ลำดับขั้นของ flow ทั้งอันThe step-by-step of a whole flow

  • Actor ใครเริ่มActor who starts it
  • Main flow ขั้นตอนปกติ 1→2→3Main flow the happy path 1→2→3
  • Alternate / Error ถ้าผิดพลาดทำยังไงAlternate / error what happens when it goes wrong

เหมาะกับ flow สำคัญที่มีหลายทางแยก เช่น การชำระเงิน การยืนยันตัวตนBest for critical, branching flows — payments, authentication.

ความสัมพันธ์กันHow they connect User Story บอก “ทำไม” (คุณค่า), FR บอก “อะไร” (พฤติกรรมของระบบ), Acceptance บอก “เสร็จเมื่อไหร่” หนึ่ง story มักแตกเป็นหลาย FR และแต่ละ FR มี acceptance ของตัวเอง The story gives the why (value), the FR gives the what (system behavior), and acceptance gives the when it's done. One story usually splits into several FRs, each with its own acceptance.

06 Non-functional / NFR

NFR — ระบบต้อง “ดี” แค่ไหน (ให้วัดได้)NFRs — how “well,” made measurable

FR บอกว่าระบบทำอะไร NFR บอกว่าทำได้ดีแค่ไหน ปัญหาที่พบบ่อยคือ NFR เขียนลอย ๆ วัดไม่ได้ กฎเหล็กคือ ทุก NFR ต้องมี ตัวเลขหรือเงื่อนไขที่ทดสอบได้

FRs say what the system does; NFRs say how well. The usual failure is a floaty, unmeasurable NFR. The iron rule: every NFR carries a number or a testable condition.

07 Acceptance / นิยามของ “เสร็จ”

Acceptance Criteria แบบ Given–When–ThenAcceptance criteria: Given–When–Then

acceptance criteria คือ “นิยามของคำว่าเสร็จ” ที่ทดสอบได้จริง เขียนก่อนลงมือสร้าง เพื่อให้ทีมและ AI รู้เป้าหมายชัด และใช้ตรวจงานตอนท้าย (M4 Testing)

Acceptance criteria are the testable definition of done. Write them before building so the team and the AI have a clear target, and reuse them to check the work later (M4 Testing).

Given–When–Then
  • Given (กำหนดให้) สถานะเริ่มต้น เช่น “ฉันอยู่หน้าจองคิว”Given a starting state — “I'm on the booking screen.”
  • When (เมื่อ) การกระทำ เช่น “ฉันเลือกเวลา 10:00 แล้วกดยืนยัน”When an action — “I pick 10:00 and tap Confirm.”
  • Then (แล้ว) ผลที่คาดหวัง เช่น “คิวของฉันปรากฏในรายการ พร้อมเลขคิว”Then the expected result — “my booking appears with a queue number.”

ตัวอย่างเต็ม — ผูกกับ FRA full example — tied to an FR

FR-05 ระบบต้องอนุญาตให้ลูกค้าจองคิวโดยเลือกช่วงเวลาที่ว่างThe system shall let a customer book a slot by choosing an available time.

ฉาก: จองสำเร็จScenario: successful booking Given มีช่วงเวลา 10:00 ว่างอยู่the 10:00 slot is free When ลูกค้าเลือก 10:00 แล้วกดยืนยันthe customer selects 10:00 and taps Confirm Then ระบบสร้างคิวและแสดงเลขคิวให้ลูกค้าa booking is created and its queue number is shown ฉาก: เวลาถูกจองไปแล้วScenario: slot already taken Given ช่วงเวลา 10:00 ถูกจองเต็มแล้วthe 10:00 slot is full When ลูกค้าพยายามเลือก 10:00the customer tries to select 10:00 Then ระบบแจ้งว่าเต็มและไม่สร้างคิวthe system says it's full and creates no booking
อย่าลืม “ทางที่ผิด”Don't forget the unhappy path มือใหม่มักเขียนแค่ฉาก “ทุกอย่างราบรื่น” แต่ requirement ที่ดีต้องบอกด้วยว่าเมื่อ ผิดพลาด (ข้อมูลว่าง เน็ตหลุด ของเต็ม) ระบบต้องตอบสนองยังไง Beginners write only the “everything works” scenario. A good requirement also says what the system does when things go wrong — empty input, lost connection, sold out.

08 Priority / จัดลำดับ

จัดลำดับความสำคัญด้วย MoSCoWPrioritize with MoSCoW

คุณจะสร้างทุกอย่างไม่ทันในหนึ่งเทอม จึงต้องรู้ว่า “อะไรคือ MVP” MoSCoW ช่วยแยกของที่ขาดไม่ได้ ออกจากของที่ไว้ทีหลัง — ตรงกับ Priority (High/Medium/Low) ใน backlog

You can't build everything in one term, so you must know your MVP. MoSCoW separates the non-negotiable from the later — mapping to the High/Medium/Low priority in your backlog.

Must — High = MVP

ขาดไม่ได้ ถ้าไม่มีระบบไม่มีความหมาย โฟกัส 3–5 FR แรกที่นี่Non-negotiable — without it the system is pointless. Your first 3–5 FRs live here.

Should — Medium

สำคัญแต่รอได้ ทำหลัง MVP เดินได้Important but can wait until the MVP works.

Could — Low

มีก็ดี ไม่มีก็ไม่เป็นไร ทำถ้ามีเวลาเหลือNice to have; skip it if time runs out.

Won't — รอบนี้ไม่ทำnot this time

ตั้งใจ “ไม่ทำ” รอบนี้ เขียนไว้กัน scope บวมDeliberately out of scope this round — write it down to stop scope creep.

เคล็ดลับ MVPMVP tip ถ้าทุก FR เป็น “Must” หมด แปลว่ายังไม่ได้จัดลำดับจริง บังคับตัวเองให้เลือก Must แค่ 3–5 ข้อ ที่พิสูจน์ว่าระบบแก้ปัญหาได้ — ที่เหลือดันลงไป Should/Could If every FR is a “Must,” you haven't really prioritized. Force yourself to keep only 3–5 Musts that prove the system solves the problem; push the rest to Should/Could.

09 Traceability / เส้นด้ายทอง

Traceability — เส้นด้ายที่ต้องไม่ขาดTraceability — the thread that must not break

requirement ทุกตัวต้องสาวกลับไปถึง “ปัญหา” ได้ และสาวไปข้างหน้าถึง “การทดสอบ” ได้ นี่คือสิ่งที่รูบริกเรียกว่า coherence และเป็นเหตุผลที่เราให้ทุกอย่างมี รหัส

Every requirement must trace back to the problem and forward to a test. This is what the rubric calls coherence, and it's why everything carries an ID.

10 Smells / กลิ่นไม่ดี

10 กลิ่นไม่ดีของ requirement10 requirement smells

ถ้าเจอสัญญาณเหล่านี้ใน SRS ให้หยุดแล้วเขียนใหม่ ก่อนที่มันจะกลายเป็นบั๊กราคาแพงในภายหลัง

Spot any of these in your SRS and rewrite before they turn into expensive bugs later.

กลิ่นเรื่องภาษาLanguage smells

  • คำกำกวม ง่าย เร็ว สวย ดี เหมาะสม ยืดหยุ่นVague words: easy, fast, nice, good, appropriate, flexible
  • ฯลฯ / และอื่น ๆ ซ่อน requirement ที่ยังไม่คิด“etc.” / “and so on” hides requirements you haven't thought through
  • และ/หรือ รวมหลายเรื่องในข้อเดียว“and/or” bundles several things into one
  • คำคลุมเครือ บางที ควรจะ โดยประมาณWeasel words: maybe, should probably, roughly

กลิ่นเรื่องเนื้อหาContent smells

  • Solution ปน requirement ระบุ React/ตาราง SQL แทนที่จะบอกพฤติกรรมSolution in the requirement: naming React / an SQL table instead of behavior
  • วัดไม่ได้ NFR ไม่มีตัวเลขUnmeasurable: an NFR with no number
  • Gold-plating ฟีเจอร์ที่ไม่มีใครขอ ไม่ผูกกับปัญหาGold-plating: a feature nobody asked for, tied to no problem
  • ยัดหลายข้อในหนึ่ง ประโยคเดียวมี 3 พฤติกรรมMultiple in one: three behaviors in a single sentence
  • ไม่มีทางที่ผิด เขียนแต่ happy pathNo unhappy path: only the happy case is written
  • ไม่มีรหัส อ้างอิงและสาวกลับไม่ได้No ID: can't be referenced or traced

11 AI-First / เขียนด้วย AI

เขียน SRS ด้วย AI — เป็น “บรรณาธิการ” ไม่ใช่ “คนพิมพ์”Write your SRS with AI — as the editor, not the typist

requirement ค้นจากผู้ใช้จริง ไม่ใช่คิดเองที่โต๊ะ AI มีหน้าที่ช่วยร่าง “ตัวเลือก (candidate)” จากหลักฐานที่คุณเก็บมา แล้วคุณเอาไปตรวจกับผู้ใช้จริงเสมอ AI ร่างได้ แต่คนเซ็นรับผิดชอบ

Requirements are discovered from real users, not invented at the desk. AI drafts candidates from the evidence you gathered; you verify them with a real user. AI may draft — a person signs off.

ทำ 3 จังหวะThree beats

1 Evidence

ป้อนหลักฐานFeed evidence

ให้ โน้ตสัมภาษณ์/สังเกตจริง ไม่ใช่แค่ปัญหาลอย ๆGive a real interview/observation note — not just an abstract problem.

2 Draft

ให้ AI ร่าง candidateAI drafts candidates

ขอ candidate user story + acceptance ที่วัดได้Ask for candidate user stories + measurable acceptance.

3 Verify

ตรวจกับผู้ใช้จริงVerify with a user

ตรวจ เขียนเป็น test แล้วตัดที่ AI เดาเองVerify, turn it into a test, cut what AI guessed.

prompt ที่แนะนำThe prompt to use

อย่าสั่งลอย ๆ ว่า “เขียน requirement ให้ระบบเรา” (AI จะเดา) ให้ ป้อนโน้ตสัมภาษณ์จริง แล้วขอ candidate ตามนี้

Don't say “write the requirements for our system” (the AI guesses). Feed a real interview note and ask for candidates like this:

อยากได้คำถามสัมภาษณ์ก่อน? ขอ AI ร่าง 5 คำถามที่ถาม “ครั้งล่าสุดที่ปัญหาเกิด” ไม่ถามเรื่องปุ่ม/หน้าจอ และไม่ชี้นำ (แนวทางจากบทที่ 4 §4.8)

  • ตัดข้อ [ASSUMPTION] ที่ยืนยันไม่ได้ และ gold-plating (ฟีเจอร์ที่ไม่มีใครขอ เช่น แต้มสะสม แชร์โซเชียล) ให้ทุกข้อผ่าน 4 quality gatescut any [ASSUMPTION] you can't confirm and gold-plating (features nobody asked for — loyalty points, social sharing); make every item pass the 4 quality gates

ตัวอย่าง SRS สั้น ๆ ของอาจารย์A short worked SRS from the instructor

นี่คือตัวอย่างจริงแบบย่อ ให้เห็น “รูปทรง” ของ SRS 7 ส่วนที่ผ่านเกณฑ์ ใช้เคส StudyMate — แอปเตือน deadline สำหรับนักศึกษา ซึ่งเป็นเคสหลักที่ใช้สอนในบทที่ 4 ของวิชา

A compact, real example showing the shape of a passing 7-part SRS, using StudyMate — a deadline-reminder app for students, the running case from the course's Chapter 4.

1. จุดประสงค์ & ขอบเขต1. Purpose & scope

ช่วยนักศึกษาไม่ให้พลาดกำหนดส่งงาน โดยจัดการงานที่มี due date และเตือนล่วงหน้าHelp students not miss deadlines by managing tasks with due dates and reminding them ahead of time.

2. ผู้มีส่วนได้เสีย (Stakeholders)2. Stakeholders

นักศึกษา (ผู้ใช้หลัก), อาจารย์ (ผู้กำหนด deadline), มหาวิทยาลัย (เจ้าของข้อมูล), ผู้ให้บริการ AI/ปฏิทินภายนอก (อาจล่มหรือรั่วข้อมูล)Student (primary user), instructor (sets deadlines), university (data owner), external AI/calendar supplier (can fail or leak).

3. Functional Requirements (เขียนเป็น user story)3. Functional Requirements (as user stories)

IDUser storyUser storyลำดับPriority
FR-1ในฐานะนักศึกษา ฉันต้องการเพิ่ม/แก้งานพร้อมกำหนดส่ง เพื่อรวมงานทั้งหมดไว้ที่เดียวAs a student, I want to add/edit a task with a due date, so that all my work sits in one place.Must
FR-2ในฐานะนักศึกษา ฉันต้องการเห็นงานของสัปดาห์นี้ เพื่อวางแผนล่วงหน้าAs a student, I want to see this week's tasks, so that I can plan ahead.Should

5. ชื่อ Use Case5. Use case names

จัดการงาน, ดูงานสัปดาห์นี้, รับการเตือน, บันทึกแผนด้วยภาษาไทย (ไดอะแกรมวาดใน M3)Manage tasks, View this week, Receive reminder, Enter plan in Thai (diagrams drawn in M3).

6. Out-of-Scope6. Out-of-scope

ไม่มีแชทกลุ่ม, ไม่มีการชำระเงิน, ไม่มี AI ติวเตอร์, ไม่อ่านข้อความจากกลุ่ม LINENo group chat, no payments, no AI tutor, no reading of LINE group messages.

7. บันทึกการใช้ AI7. AI-use log

ใช้ AI ช่วยร่าง user story ชุดแรกจากบันทึกสัมภาษณ์ แล้วทีมตรวจทุกข้อกับ 4 ประตูคุณภาพและแก้ให้วัดได้เองAI drafted the first set of user stories from interview notes; the team checked each against the four quality gates and made them measurable.

สังเกตเส้นด้ายNotice the thread ปัญหา (กลัวส่งงานสาย) → FR-3 (Must = MVP) → NFR-2 วัดได้ → acceptance มีทั้งฉากที่เตือนและฉากที่เงียบ นี่คือ Golden Thread ที่วิชาใช้ให้คะแนน และเป็นเคส StudyMate เดียวกับที่สอนในบทที่ 4 Problem (fear of submitting late) → FR-3 (Must = MVP) → measurable NFR-2 → acceptance with both a reminder path and a silent path.
