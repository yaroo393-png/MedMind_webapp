Wider scope: the 2023 edition applies to whole ICT products, which the standard says include software, hardware, firmware, data and communication infrastructure, not just software. 2. Systems grow fast: Flexibility adds scalability because cloud systems must grow with their users.

เพื่อนในทีมอ่านโค้ดของเราก่อนรวมเข้า main ซึ่งก็คือหน้าที่ของ Pull Request ที่เรียนใน Ch6 จับได้ทั้งบั๊กเชิงตรรกะ ชื่อที่อ่านแล้วงง และกรณีที่ลืม และยังทำให้ความรู้กระจายในทีม ไม่ติดอยู่กับคนเดียวA teammate reads your code before it is merged into main, which is what a Pull Request is for (Ch6). Linter (static analysis)

โปรแกรมที่อ่านโค้ด โดยไม่ต้องรัน แล้วเตือนเรื่อง style ตัวแปรที่ประกาศแต่ไม่ใช้ และรูปแบบที่มักเป็นบั๊ก ทำงานเร็ว สม่ำเสมอ และรันได้ทุก commit ตัวอย่างเช่น ESLint สำหรับ JavaScript หรือ Ruff สำหรับ PythonA program that reads code without running it and flags style issues, unused variables and patterns that are often bugs. Fast, consistent, and it runs on every commit. Examples: ESLint for JavaScript, Ruff for Python.

จำง่ายๆIn plain terms linter คือ spell-check ของโค้ด ส่วน code review คือให้เพื่อนพิสูจน์อักษรเรียงความ สองอย่างนี้ไม่ได้แทนกัน spell-check ไม่รู้ว่าเนื้อหาผิด และเพื่อนอาจมองข้ามคำสะกดผิด ยิ่งใช้ AI เขียนโค้ด ยิ่งต้องมีทั้งสองอย่าง เพราะ AI เขียนได้เร็วกว่าที่คนจะอ่านทัน A linter is spell-check for code; a code review is a classmate proof-reading your essay. They do not replace each other: spell-check cannot tell the argument is wrong, and a reader may miss a typo. With AI-written code you need both even more, because AI writes faster than people can read.

04 Big three / นิสัยความปลอดภัย 3 ข้อ

Security: นิสัย 3 ข้อที่กันความผิดพลาดของมือใหม่ได้เกือบหมดSecurity: three habits that stop most beginner mistakes

#1

Validate input

อย่าเชื่อข้อมูลจากผู้ใช้หรือ browser ตรวจชนิด ความยาว และช่วงค่า ที่ฝั่ง server ก่อนใช้หรือบันทึกNever trust data from the user or the browser. Check type, length and range on the server before using or storing it.

ทำไมต้อง server: ผู้ใช้ปิด JavaScript หรือส่ง request ตรงโดยไม่ผ่านหน้าเว็บได้เสมอ การตรวจใน browser ช่วยเรื่องความสะดวก แต่ไม่ใช่ความปลอดภัยWhy the server: users can switch off JavaScript or send requests directly, skipping the page. Browser checks are for convenience, not security.

#2

Access control

ผู้ใช้ที่ login แล้วเห็นได้เฉพาะข้อมูลของตัวเอง ทุก request ต้องถามสองคำถาม "คุณเป็นใคร" และ "ข้อมูลนี้ของคุณไหม"A logged-in user may see only their own data. Every request must ask two questions: "who are you?" and "is this yours?"

การ login (authentication) ตอบคำถามแรก ส่วน access control (authorization) ตอบคำถามที่สอง ระบบที่มีแค่ login ยังไม่ปลอดภัยLogin (authentication) answers the first question; access control (authorization) answers the second. Login alone is not enough.

#3

No secrets in the repo

password, API key และ token ห้ามอยู่ในโค้ดหรือใน Git history ให้เก็บใน .env และใส่ .env ไว้ใน .gitignorePasswords, API keys and tokens never go in the code or the Git history. Keep them in .env and list .env in .gitignore.

ถ้าเผลอ commit ไปแล้ว ลบออกจากโค้ดไม่พอ เพราะ history ยังเก็บไว้ ต้อง revoke key นั้นที่ผู้ให้บริการแล้วออก key ใหม่If one was committed, deleting it is not enough because history keeps it. Revoke the key at the provider and issue a new one.

จำง่ายๆIn plain terms นึกถึงร้านค้า ตรวจของที่เข้าประตู (validate input) เฉพาะพนักงานเปิดลิ้นชักเงินได้ (access control) และอย่าแปะกุญแจไว้ที่ประตู (no secrets in the repo) Picture a shop: check what comes through the door (validate input), only staff can open the till (access control), and never tape the keys to the door (no secrets in the repo).

1. ช่องอายุกรอก -5 แล้วระบบบันทึกได้1. The age field accepts -5 and saves it.Validate input
2. เปลี่ยน order_id ใน URL แล้วเห็นใบสั่งซื้อของคนอื่น2. Changing order_id in the URL shows someone else's order.Access control (IDOR)

05 IDOR / ช่องโหว่ที่เจอบ่อย

ถ้าผู้ใช้เปลี่ยน id ได้ เขาก็อ่านข้อมูลของคนอื่นได้If the user can change the id, they can read your data

IDOR ย่อมาจาก Insecure Direct Object Reference เป็นรูปแบบหนึ่งของ broken access control ซึ่ง OWASP Top 10 ปี 2021 จัดเป็นความเสี่ยงอันดับ 1 ของ web applicationIDOR stands for Insecure Direct Object Reference. It is a form of broken access control, which the OWASP Top 10 (2021) ranks as the number one web-application risk.

ผิด: server เชื่อ id จาก URLWrong: the server trusts an id from the URL
# anyone logged in can swap the number
GET /api/notes?user_id=1042

def get_notes(user_id):
    return db.notes.where(owner=user_id)
# whose id is this? nobody checked

ผู้ใช้ 1042 แก้เลขเป็น 1043 แล้วได้โน้ตของอีกคนทันทีUser 1042 changes it to 1043 and gets someone else's notes.

ถูก: เอาตัวตนจาก sessionRight: take identity from the session
# the id comes from WHO is logged in
GET /api/notes

def get_notes(session):
    me = session.user
    return db.notes.where(owner=me.id)

ผู้ใช้ไม่มีช่องให้แก้ว่าเป็นใคร เพราะ server รู้เองจากการ loginThere is nothing for the user to edit; the server already knows who they are from the login.

  1. มันคืออะไรWhat it isserver ตัดสินว่าข้อมูลเป็นของใครจากค่าที่ผู้ใช้แก้ได้ เช่น id ใน URL ฟอร์ม หรือ requestThe server decides whose data it is from a value the user can edit, such as an id in the URL, a form or the request.
  2. ทำไมอันตรายWhy it is dangerousใครก็ได้ที่ login แล้วเปลี่ยนตัวเลขเดียว ก็อ่านหรือแก้ข้อมูลของคนอื่นได้ "ผ่านเทสต์" ได้ด้วยถ้าเทสต์ลองแค่กรณีผู้ใช้สุจริตAnyone logged in can change one number and read or edit another person's data. It can even "pass the tests" if the tests only try honest users.
  3. แก้อย่างไรHow to fix itเอาตัวตนจาก session ที่ login และตรวจทุก request ว่าข้อมูลนั้นเป็นของผู้ใช้คนนี้Take identity from the authenticated session and check on every request that the data belongs to this user.
แนวข้อสอบExam angle short answer "อธิบาย IDOR และวิธีแก้" ต้องตอบให้ครบ 3 ส่วนข้างบน คำตอบ "ซ่อน id ไม่ให้เห็น" หรือ "เช็กว่า id เป็นตัวเลข" ยังไม่แก้ปัญหา เพราะผู้ใช้ยังส่ง id ของคนอื่นมาได้ For the short answer "explain IDOR and how to fix it", cover all three parts above. "Hide the id" or "check the id is a number" does not fix it, because the user can still send someone else's id.

06 Privacy / ข้อมูลส่วนบุคคล

ข้อมูลส่วนบุคคลเป็นหน้าที่ตามกฎหมาย: PDPAPersonal data is a legal duty: PDPA

พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 (PDPA) มีผลบังคับใช้เต็มรูปแบบตั้งแต่ปี 2565 ใครเก็บข้อมูลที่ระบุตัวคนได้ เช่น ชื่อ เบอร์โทร อีเมล รูปหน้า ตำแหน่ง มีหน้าที่ตามกฎหมาย หัวใจที่ต้องจำมี 3 คำThailand's Personal Data Protection Act B.E. 2562 (2019), fully in force since 2022. Anyone holding data that identifies a person, such as name, phone, email, face or location, has legal duties. Remember three words.

Consent

ขอก่อน และบอกว่าเอาไปทำอะไรAsk first, and say why

เก็บเมื่อเจ้าของข้อมูลยินยอม โดยรู้วัตถุประสงค์ชัดเจนด้วยภาษาที่เข้าใจง่ายCollect with the person's informed consent, for a stated purpose, in plain language.
Minimise

เก็บให้น้อยที่สุดCollect the least

ฟีเจอร์ไม่ต้องใช้ ก็ไม่ต้องเก็บ ทุกช่องที่เกินมาคือภาระที่ต้องปกป้องIf the feature does not need it, do not store it. Every extra field is a liability.
Protect

ดูแล และเคารพสิทธิGuard it and honour rights

เก็บอย่างปลอดภัย จำกัดคนเห็น และให้เจ้าของข้อมูลขอดู แก้ไข หรือลบได้Store it securely, limit who sees it, and let people see, correct or delete their data.
สำหรับโปรเจกต์ของเราFor your project prototype ใช้ ข้อมูลจำลอง เท่านั้น ห้ามมีชื่อ เบอร์ อีเมล หรือรูปของคนจริงใน repo และใน Git history Prototypes use fake data only. No real names, phone numbers, emails or photos of real people in the repo or its Git history.

ตัวอย่าง sprint 10 วัน งาน 40 pointsExample: 10-day sprint, 40 points

SA1 (Ch8) Explain what an IDOR vulnerability is and how to fix it. Give one example.

ดูคำตอบตัวอย่างShow model answer

คำตอบ 3 คะแนน: IDOR คือการที่ server ตัดสินว่าข้อมูลเป็นของใครจาก id ที่ผู้ใช้แก้ได้ เช่น ใน URL หรือฟอร์ม ผู้ใช้จึงเปลี่ยน id แล้วเห็นหรือแก้ข้อมูลของคนอื่นได้ เป็น broken access control ตัวอย่าง เปลี่ยน user_id=1042 เป็น 1043 แล้วอ่านโน้ตของอีกคน วิธีแก้คือเอาตัวตนจาก session ที่ login และตรวจทุก request ว่าข้อมูลเป็นของผู้ใช้นั้น3-point answer: IDOR is when the server decides whose data it is from an id the user can edit, such as in the URL or a form, so a user can change the id and see or edit another person's data. It is broken access control. Example: changing user_id=1042 to 1043 shows someone else's notes. Fix: take identity from the authenticated session and check on every request that the data belongs to that user.

ได้ 1 คะแนนถ้าตอบแค่ "ซ่อน id" หรือ "เช็กว่าเป็นตัวเลข" เพราะยังไม่แก้ต้นเหตุOnly 1 point for "hide the id" or "check it is a number", because the cause is not fixed.

SA2 (Ch8) Why is checking input only in the browser not enough? What should be done instead?

ดูคำตอบตัวอย่างShow model answer

คำตอบ 3 คะแนน: ผู้ใช้ควบคุม browser ได้ทั้งหมด จะปิด JavaScript หรือส่ง request ตรงไปที่ server โดยไม่ผ่านหน้าเว็บก็ได้ การตรวจใน browser จึงถูกข้ามได้ ต้อง validate input ที่ฝั่ง server ทุกครั้ง (ชนิด ความยาว ช่วงค่า) การตรวจใน browser มีไว้ช่วยผู้ใช้ให้รู้ข้อผิดพลาดเร็ว ไม่ใช่เพื่อความปลอดภัย3-point answer: The user controls the browser completely; they can switch off JavaScript or send requests straight to the server without the page, so browser checks can be skipped. Input must always be validated on the server (type, length, range). Browser checks only help users notice mistakes early; they are not security.

SA3 (Ch9) An AI assistant suggests one task, "Build the whole app," assigned to the best coder. Give two problems with this plan and one fix based on Chapter 9.

ดูคำตอบตัวอย่างShow model answer

คำตอบ 3 คะแนน: ปัญหา 2 ข้อจาก (1) task ใหญ่เกินจนประมาณและติดตามความคืบหน้าไม่ได้ (2) ไม่มีการแบ่งงาน คนอื่นในทีมไม่มีส่วนร่วม (3) ฝากทุกอย่างไว้กับคนเดียวเป็น single point of failure ถ้าคนนั้นป่วยหรือออก โปรเจกต์หยุด (project risk) วิธีแก้: แตกเป็น task ขนาด FR ประมาณขนาดแต่ละ task กระจายเจ้าของบน board และทบทวนความคืบหน้าทุก sprint3-point answer: Two problems from: (1) the task is too big to estimate or track; (2) the work is not shared, so the rest of the team is left out; (3) relying on one person is a single point of failure: if they are ill or leave, the project stops (a project risk). Fix: split it into FR-sized tasks, size each one, spread owners across a board, and review progress every sprint.

SA4 (Ch9) Explain the difference between a project risk, a product risk and a business risk. Give one example of each.

ดูคำตอบตัวอย่างShow model answer

คำตอบ 3 คะแนน: project risk กระทบตารางเวลาหรือทรัพยากร เช่น สมาชิกออกจากทีม; product risk กระทบคุณภาพหรือประสิทธิภาพของ product เช่น ระบบช้าเกินเมื่อข้อมูลเยอะ; business risk กระทบเป้าหมายขององค์กรหรือตลาด เช่น ทำเสร็จแล้วไม่มีใครต้องการ (Sommerville §22.1)3-point answer: A project risk affects the schedule or resources, for example a member leaves the team. A product risk affects the quality or performance of the product, for example the system is too slow with a lot of data. A business risk affects the organisation's goals or market, for example nobody needs the product once it is built (Sommerville §22.1).
